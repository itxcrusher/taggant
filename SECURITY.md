# Security

## Reporting a vulnerability

Use GitHub's private vulnerability reporting on this repository (Security tab, "Report a vulnerability"). It reaches the maintainer without a public issue. Say what you found, how to reproduce it, and which package. A reply within seven days; a fix or a stated reason within thirty.

Do not open a public issue for something exploitable until it has been fixed and published.

## What this project is responsible for

Three things ship to people who did not build them, and each has a stated boundary.

**A published bundle** is a folder of static files that any host serves as-is, including one that sets no headers. Every asset in it sits at its own address on the host's origin, and a browser opening the address of a document runs whatever the document says. So the property a bundle holds is that no asset in it is served as a document or sniffed as one: every asset is identified from its own bytes and its extension is set from those bytes, never from the name it arrived under, so the type a host serves and the signature a browser reads always agree. Rasters, video and audio pass through once their signatures say what they are, an SVG is rendered to a PNG by libvips, and anything else is refused by name, including HTML under any extension, UTF-16 text, a container whose brand a browser would not play, a gzipped file, and a file whose bytes match no format the bundler publishes (`packages/bundler/src/assets.ts`). Said exactly, because the looser sentence this replaces ("a bundle carries no document") is not literally true: a file of eleven bytes of PNG signature followed by HTML is HTML, and it ships, as `.png`, where no host serves it as a document and no sniffing rule reads it as one. What is refused is the file being served or read as something that runs. The renderer has no script engine and no network stack and is handed a buffer with no base location, so an SVG that references another host or a local file renders those references as nothing. That is measured rather than assumed, by every route this project or a review of it has found, and in two ways, because one measurement cannot see both kinds. Most routes would draw the file's own content into the picture: an XInclude as text, as XML, by relative path, with an xpointer or through a fallback; an external, parameter or external-DTD entity, the last of them through a real definition on disk that declares one; an image, `use` or filter reference by `href` or by `xlink:href`; a pattern, a marker, a `tref`, a `foreignObject` holding an XHTML image; and an include nested inside a `data:` image. Those are measured in pixels: each document's only visible content is what its reference would bring in, so one opaque pixel is a leak. Two more would apply a local stylesheet, which draws no file content and so cannot be seen in pixels at all; those documents draw a shape with no fill while the stylesheet sets one, so the paint itself is the measurement. Each group has a `data:` control that must paint, or an empty render would prove only that the renderer drew nothing. One route is named as not covered rather than counted: a font whose source is a local file can only become the shapes of characters the document already chose to draw, so pixels cannot show whether the file was opened, and measuring it would need a real font on disk to compare against the fallback (`packages/bundler/test/nothing-reaches-out.test.ts` says so where the route would be). What rendering moves rather than removes is the parser. An SVG is read by a native library on the publishing machine instead of by a reader's browser, and that library can be held and can be crashed: a dilate filter of radius 500 units ran for four and a half minutes, and a convolution matrix of order thirty took the process down with an illegal instruction. So the renderer runs in a process of its own with a clock over it (`packages/bundler/src/render-child.ts`): a document that holds it is killed at twenty seconds and refused, a document that crashes it is refused, and the process that called it is still running to say so. That is driven twice: at the bundler's own entry point (`packages/bundler/test/render-process.test.ts`), and through a running console, which is asked to publish the document that killed the renderer outright and has to come back with a message naming the file and go on serving (`apps/console/test/server.test.ts`). Renders run one at a time, so a second clock bounds all of them together at two minutes, or a manifest naming enough drawings would hold a publish for twenty seconds each. A vulnerability in the renderer would run with the publisher's rights inside that process and never a reader's; the renderer arrives pinned with `sharp` and is updated with it. Two earlier versions of this control read SVG and decided what was safe in it, and adversarial reviews produced twelve bypasses between them, ten executing or fetching in two browsers; the reason for rendering is that pixels cannot run or fetch, and no inspection has to be complete. Asset paths in a manifest are resolved against the manifest's own directory and refused if they leave it. The bytes written are the bytes that were read and rendered, not a second read of the path. A test feeds every payload those reviews produced through a real publish and requires that nothing a browser would treat as a document reaches the folder (`packages/bundler/test/nothing-reaches-out.test.ts`); a second opens a published bundle in a real browser and fails on any request that leaves the origin (`packages/bundler/test/browser/served.browser.test.ts`).

**The resolver** answers GS1 Digital Link requests from a JSON table. It stores nothing: no database, no cookie, no address, no user agent. Scan events go to standard output as one line each, and counts on `/metrics` reset when the process does. Where a redirect sends a client is the table's link with the request's own query string appended, which the standard requires and which is how a printed code carries a campaign parameter; the part that comes from the table is the address, and the part that comes from the request is the query. It does not rate-limit, and that is deliberate: it holds no state a flood could corrupt and costs only the CPU of a table lookup, so a limit belongs in the proxy an operator puts in front of it, which is where the compose file puts one. Nothing a request carries reaches the subject URL this resolver publishes. That subject is the anchor of every linkset, all three `Link` references including `owl:sameAs`, and `resolverRoot` in the description file, and it is `--origin`, which is required: the resolver refuses to start without one and checks that it is an http or https URL with no query or fragment. It used to fall back to the `Host` header, so `Host: evil.example` published that host as the identity of the operator's products, and with an origin set it still appended the path the caller wrote in front of the identifier; an adversarial pass found both, and found that the test written for the first could not fail, because `fetch` silently replaces a caller-set `host`. A resolver behind a proxy sets its origin rather than the resolver reading `X-Forwarded-*`, which would hand the decision back to whoever sends the request.

**The console** binds to `127.0.0.1` by default and is meant to run on the operator's own machine or inside their own network. It has no accounts and no authentication, because it has no users other than the operator, and everything it does it does with the file-system rights of whoever started it. Given any other `--host` it prints a warning saying exactly that and then binds anyway, because binding it somewhere reachable is a decision and not one to make by leaving a flag at its default; the compose file binds it to `127.0.0.1:4000`. An upload is stored in the operator's own workspace under a rebuilt version of its filename, not under its own and not by its content; content addressing happens when a bundle is published, and every rule above applies then, so an SVG the bundler refuses is refused at publish and the operator is told why.

**Two operators at once, which is an integrity property rather than an access one.** Every write the console makes goes to a temporary name and is renamed into place, and writes to one experience, one link table or one publish destination are queued behind each other, so no reader ever sees a half-written file and two requests cannot interleave a read and the write that follows it. That holds inside one process and nowhere else: two consoles on one workspace both read a file, both decide what the next version of it is, and one of the two edits is gone with both operators told it was saved. So one console at a time per workspace and per link table, and the console checks it rather than asking to be trusted about it, taking a lock in the workspace and beside the link table when it starts and refusing to open either one a running console holds (`apps/console/src/one-console.ts`). A lock left by a crash on the same machine is taken over and the takeover is printed; one taken on a machine or in a container this one cannot ask about is refused with the file named, because a process id means nothing off the machine that wrote it.

## What is collected, kept and sent

Nothing here is a service anyone else runs, so this is not a privacy policy for a product. It is the list of what the three things that ship actually touch, so that whoever deploys them can write their own with the facts in front of them, and so that a reader can check each line against the code rather than take it.

**A bundle, in a viewer's browser.** The camera is asked for by the browser, frame by frame, and never recorded, stored or transmitted: recognition runs in the page, on a worker, on pixels that are gone the moment the next frame arrives. A bundle has no analytics, no cookie, no local storage and no identifier for a viewer, and it makes no request off its own origin, which is the claim two tests exist to keep: one reads every file a bundle ships and refuses an absolute address, the other opens a published bundle in three browser engines and fails on any request that leaves the origin. There is nothing to opt out of and nothing to delete, because nothing was kept.

**The resolver, on whoever runs it.** It answers from a table in a file. It has no database and writes no file. Each scan becomes one JSON line on standard output holding the identifier that was scanned, the moment, the link the table chose, and the language tag that decided the choice when a language did; no address, no user agent, no cookie, no referrer, nothing that identifies a person. Two of those are narrower than they were, because an adversarial pass found personal data in both: the line recorded the resolved target, which carries the caller's query string, so a scan of a code printed with `?email=` put an email address in the log; and it recorded the raw `Accept-Language` header rather than the tag that matched, which is a four kilobyte field when somebody sends four kilobytes. Standard output carries nothing but these lines now: the start-up banner and the reload notices moved to standard error, so a collector reading JSON is handed only JSON. Those lines belong to the operator's own logging, which is where any retention decision lives; `/metrics` holds counts in memory only and they reset when the process restarts.

**The console, on the operator's machine.** It has no accounts, no cookies and no users other than whoever started it, and it binds to the loopback address by default. What it writes, it writes to three directories the operator owns and mounts: the workspace it authors in, the folder it publishes to, and the resolver's link table. It sends nothing anywhere.

Nothing in this repository reads an environment variable or holds a credential, and a test over every tracked file refuses the shapes of one (`packages/bundler/test/no-control-characters.test.ts`).

## What it is not responsible for

- The host serving a bundle. A bundle is designed to be safe on a host that sets no headers, and a host that sets restrictive ones only helps.
- The camera. The runtime asks the browser for it and never records or transmits a frame; recognition runs in the page, on a worker, and nothing leaves the device.
- The link table's contents. The resolver redirects where the table says; whoever writes the table decides where scans go.

## The suite never opens a real camera

Every camera in the test suite is a canvas. `navigator.mediaDevices` is replaced on the instance and on `Navigator.prototype` before any page script runs, no browser is launched with a fake-device flag, and a test scans the tree for any such flag or permission grant (`packages/runtime/test/no-real-camera.test.ts`). A contributor's webcam does not turn on because they ran the tests.
